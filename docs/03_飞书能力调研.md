# 第三部分：飞书（Feishu / Lark）API 能力详细拆解

飞书是三个平台里面**能力最丰富、也是统一抽象难度最高的平台**。

原因：

企业微信更偏：

> 企业通讯 + 客户管理

钉钉更偏：

> 企业管理 + OA

飞书更接近：

> 企业数字化操作系统

它不仅提供 IM，还提供：

- 云文档
- 多维表格
- 知识库
- 云空间
- 日历
- 审批
- 邮件
- 会议
- 自动化

因此，中台设计不能简单做：

```
飞书 Adapter
=
消息 Adapter
```

而应该：

```
Feishu Connector

├── Identity
├── Organization
├── Messaging
├── Drive
├── Document
├── Spreadsheet
├── Bitable
├── Wiki
├── Calendar
├── Approval
├── Attendance
└── Event
```

# 2. Authentication 认证体系

## 2.1 飞书认证模型


飞书采用：

```
app_id
+
app_secret

↓

tenant_access_token
```


接口：

```
POST

/open-apis/auth/v3/tenant_access_token/internal
```


请求：

```json
{
    "app_id":"cli_xxx",
    "app_secret":"xxx"
}
```


返回：

```json
{
    "code":0,

    "tenant_access_token":
    "t-xxxx",

    "expire":7200
}
```


---

# 2.2 统一抽象

和企业微信一致：

```
Credential
```

统一：

```json
{
    "provider":"feishu",

    "tenant_id":"company001",

    "credential":{

        "app_id":"",
        "secret":""

    }
}
```

# 3.1 User 用户


## 飞书 API

查询用户：

```
GET

/open-apis/contact/v3/users
```


返回：

```json
{
"data":{

"items":[

{

"user_id":"ou_xxxxx",

"union_id":"on_xxxxx",

"name":"张三",

"mobile":"138xxx",

"email":"xxx",

"department_ids":[
"od_xxx"
]

}

]

}
}
```


---

# 统一 User 模型


三个平台最终：

```
UnifiedUser
```


设计：

```json
{
"id":"uuid",


"name":"张三",


"mobile":"",


"email":"",


"avatar":"",


"status":"active",


"accounts":[

{
"provider":"feishu",

"external_id":
"ou_xxxxx",

"union_id":
"on_xxxxx"

}

]

}
```


---

## 为什么保留 external_accounts？


因为：

同一个员工：

企业微信：

```
userid=zhangsan
```


飞书：

```
open_id=ou_xxx
```


钉钉：

```
userid=xxx
```


不能强行映射。


所以：

```
User

 |
 +-- Identity Account
```

# 对统一中台最大的影响

飞书告诉我们：

不能设计：

```
One API = 三个平台共有能力
```

而应该：

```
Core Model
+
Capability Extension
```


最终架构：

```
Unified API

       |
       |

Core Capability

(User
 Message
 File)


       +

Extension Capability

(Document
 Bitable
 Wiki)

```
